# Project

Original 8x8 drag-and-drop block puzzle. NOT Tetris — no falling pieces,
no rotation, no timer. Never reference Tetris in code, assets or naming.

## Rules
- TypeScript strict. Vite + Canvas 2D. No game engine, no runtime deps.
- board.ts stays pure: no DOM, no rendering, no imports from other modules.
  It is the only thing with tests and the only place real bugs hide.
- The piece generator never reads the score or adapts to the player.
  Difficulty comes from the board filling up. This is non-negotiable.
- Pointer Events only — one code path for mouse and touch.

## Rules of play
- A row, a column or a 2x4 region (the board is eight such regions) clears when full. Crossing
  clears all fire in one pass. The region rule lives in board.ts and is covered by tests.
- Modes: classic, daily (date-seeded, first attempt is the record, replays are practice), weekly
  challenge, journey (pre-filled levels with goals), zen (no game over), and a 14-day daily archive.
- Every random game is seeded, so a shared link replays the exact same pieces.

## Structure
- Pure, tested modules (no DOM): board, rng, streak, share, meta, challenge, journey, weekly, solver, map.
- main.ts holds the game loop, board rendering and input. gfx.ts has drawing primitives and layout
  (including the shared candy look: sheets, ribbons, candy buttons, bubbly lettering),
  overlays.ts the screens drawn over the game, mapView.ts the journey map (its path, worlds and
  scenery layout are in map.ts), progress.ts stats/badges/themes/streak, records.ts saved
  records. Keep new logic in a pure module where it can be tested.
- public/par.json is each day's par, played offline by a greedy bot (src/solver.ts).
  Regenerate it with `npm run par` whenever the rules or the piece set change, because par depends on both.
- src/levelTable.ts calibrates the 150 journey levels (generated by `npm run levels`, same trigger).
  `npm run validate` checks journey, weekly goals and region shapes against the bot.

## Scope
No coin or booster economies, no obstacle or gem cells, and no adaptive difficulty. Do not add
them unless I ask.

Monetisation and measurement exist because I asked for them (src/ads.ts, entitlements.ts,
analytics.ts). They are built to stay inert until configured, and they must never touch the rules:
- None of them may alter the piece generator, the board, the scoring or the leaderboard's replay
  verification. Everything sold or shown is cosmetic or removes an interruption.
- Ads go only through AdProvider. A reward is granted only on a `completed` outcome, and never in
  the daily, the weekly or a challenge (mayOfferRewarded). With no ad network on the page the null
  provider is used and the game plays exactly as before.
- Entitlements: the client's copy is a cache for drawing the shop. A purchase counts only after a
  server has verified it (not built yet), the same way a score counts only after replay.
- Analytics: anonymous and self-hosted, with a closed list of event names, no third-party SDK and no
  personal data. Off unless VITE_ANALYTICS_ENDPOINT is set.

The one backend is the leaderboard (api/ routes and src/server/), kept deliberately small:
- Anonymous. A random player id and a public nickname; no accounts and no personal data.
- Scores are never trusted. The client sends its list of moves and the server replays them with the
  same board.ts, pieces.ts and rng.ts, so only a legal game can score. Bump RULES_VERSION in
  src/verify.ts whenever scoring, the rules or the piece set change.
- It is optional: the game hides every leaderboard control unless /api/health reports a store.
- Storage is Redis over REST (Vercel's Redis integration). `npm run dev:api` runs the same routes
  against an in-memory store for local testing.
